# T1, grammar and meaning of Flambda types: status

Branch `flambda2-rocq/T1-grammar`. Files, all in
`middle_end/flambda2/types/rocq/`:

- `FlambdaTypeGrammar.v`: the grammar (`flambda_type` and the types
  defined with it), `kind`, and the creation functions of
  `type_grammar.ml` and `more_type_creators.ml` that the statements
  use. Definitions only; reviewed against the OCaml like
  `FlambdaModel.v`. Its header says, constructor by constructor, what
  the model has.
- `FlambdaTypeMeaningSpec.v`: `type_satisfied statics vars v t`, what it
  reads of a value, and the statements.
- `FlambdaTypeMeaningProofs.v`: the proofs, one equation for each
  constructor (hint database `type_satisfied`), and the examples.

Today's `FlambdaTypesSpec.v` and `FlambdaTypesProofs.v` are untouched
and still build; `FlambdaAliases*` and the validator use them.

## Done

First merge request, at 0921c0d827 (with R1): the grammar and the
denotation.

- The grammar, in full but for `Array` (needs subkinds; the machine has
  no arrays), the `rec_info` of a function type and the head of a
  `Rec_info` type (the terms have no `Rec_info`).
- `type_satisfied`, a structural `Fixpoint` on the type, so it unfolds
  and computes. Maps inside types are read through `lookup` only.
- 35 statements, all proved: what the map combinators mean; the kind of
  a value that has a type; `Unknown`, `Bottom`, aliases; one equivalence
  for each creation function (`null`, `any_non_null_value`,
  `create_variant`, `tag_immediate`, `these_tagged_immediates`,
  `any_block`, `immutable_block`, `box_number`,
  `this_immutable_string`, `exactly_this_closure`, the three relation
  types, ...); the row-like structures, the closures entry and the
  environment extension by `lookup`.
- Examples for every constructor: a value that has a type and one that
  has not (module `Examples` of the Proofs file).
- Validation at 0921c0d827: `make -C rocq -j16 all` and
  `make -C rocq assumptions` pass (174 axioms, those of the ledger; the
  Flambda 2 statements depend on the 7 of its section and no other);
  the semantics tests pass; nothing extracted changes.

Second merge request, on top: what T2 to T7 need.

- `FlambdaTypeGrammarProofs.v`: `types_induction`, induction on the
  grammar (Rocq gives none for a type defined with seven others that
  holds lists and maps of itself). Every proof by induction on types
  goes through it.
- `free_variables` of a type (`Type_grammar.free_names`, the variables
  only), and `type_satisfied_coincide`: the meaning depends on the
  environment only through them. `type_satisfied_bind`: binding a
  variable that a type does not mention changes nothing (for T2, under
  a binder).
- `type_satisfied_statics_extend`: a type keeps its values when the
  static environment grows (for T2: `Let_static`, and handlers that run
  later; with `FlambdaWellFormedSpec.run_extends_statics`).
- The same two for environment extensions.
- `is_obviously_bottom`, `is_obviously_unknown`,
  `row_like_for_blocks_is_bottom` with what they mean;
  `heads_compatible`: heads of different constructors have no value in
  common (the last case of `meet_head_of_kind_value_non_null`), for T4
  and T6; `unknown_is_top` for T5.
- What a relation says of the value it is about (`relation_is_null`,
  `relation_is_int`, `relation_get_tag`): what
  `reduce_inverse_relations` deduces, for T4, T6 and S1.
- `unknown`, `bottom` and `alias_type_of` written out by cases, so that
  they extract without `Obj.magic` (the first request had a helper of
  rank 2, `type_of_kind`).
- How to prove with the meaning: one equation for each constructor
  (`autorewrite with type_satisfied`), the `_iff` lemmas by `lookup`
  for the row-like structures, entries and extensions; `simpl` and
  `cbn` leave `type_satisfied` alone once the Proofs file is loaded.

- Validation of the second request (the commit before the last "lines
  for the shared lists"): `make -C rocq -j16 all` passes (147 claims),
  `make -C rocq assumptions` passes with the same axioms, the semantics
  tests pass, nothing extracted changes. The grammar was also extracted
  on the side (`flambda_type`, the creation functions,
  `free_variables`): it is plain OCaml, with no `Obj`, and compiles.

## Agreed with other streams

With C1 (primitives; its note is to be
`middle_end/flambda2/rocq/requests/C1-primitives.md`):

- Values after C1: `Value_block tag fields` and
  `Value_boxed_number (contents : const)` are added; nothing changes.
- C1 defines, in the semantics, `block_of statics v : option (Z * list
  value)`, `boxed_number_of statics v : option const` (only for the
  boxable kinds), `string_of statics v : option (list Z)` and
  `kind_of_value : value -> flambda_kind`. Until its epoch they are
  defined in `FlambdaTypeMeaningSpec.v` with the same names and types,
  over today's machine (symbols only); the epoch deletes mine.
- A closure and a boxed number are not blocks for `block_of`: the heads
  of kind value are disjoint, as `Meet` assumes.
- `eval_prim` will take the static environment. `Is_int` has the
  compiler's flag `variant_only`; the relation of types is the
  `variant_only = true` one: 1 on a tagged immediate, 0 on a block, no
  value elsewhere. `Get_tag`: the tag of a block, no value elsewhere.
  `Is_null`: 1 on `Null`, 0 on a tagged immediate and on anything
  allocated, no value on `Poison`, naked numbers and unbound symbols.
  My `relation_holds` has exactly these cases; after the epoch it is to
  be defined by `eval_prim`.
- Open, for C1 to check: C1's list of boxable kinds had no
  `Naked_mask`; `Flambda_kind.Boxable_number` has it, and so has
  `boxable_number` here.
- C1 flags, for the human: a block made by `Make_block` and a symbol
  bound to an equal static block are different values at exit. T1 does
  not depend on it; T6 (reification to symbols) will.

With C2 (kinds):

- The kinds are those of `FlambdaModel.v`; `kind : flambda_type ->
  flambda_kind`.
- `type_satisfied statics vars v t -> kind_of_value v = kind t`, with
  no premise (`type_satisfied_kind_statement`).
- A variable's kind comes from its binder, and C2's invariant of a
  state gives `kind_of_value` of its value: for T2's `env_satisfies`.
- Block shapes are defined here (`block_shape`); if terms come to need
  them they move to `FlambdaModel.v`. Value slots get kinds from a
  table given to C2's checker.

With C3 (sets of closures):

- `function_slot : Type := positive` will be in `FlambdaModel.v` under
  that name; mine goes then.
- C3 defines `closure_in_set statics v : option (function_slot * list
  (function_slot * code_id) * list (value_slot * value))` and
  `project_function_slot statics move_from move_to v : option value`.
  Until its epoch they are defined in `FlambdaTypeMeaningSpec.v` with
  the same names and types.
- Today's closures, whose function slot has no name, are read as the
  closure at `unnamed_function_slot` (C3 takes the constant into the
  semantics: my option (a)). The unnamed forms are meant to go later;
  nothing may depend on the constant being 1.
- C3's request is `middle_end/flambda2/rocq/requests/C3-closures.md` on
  its branch. From a symbol, `project_function_slot` gives the symbol
  that the set names for the slot, bound or not: the meaning of
  `closure_types`, which asks the type of the result, is right as it
  stands; only a claim that the result is a closure of the same set
  needs C3's premise `static_set_bound`.

  never edits my files; I delete mine when both are merged.
