## The design, in one paragraph

Constructors are added and none is changed. `named` gains
`Closure_of_set slot function_decls value_slots` (the closure at one
function slot of a newly made set), `Project_function_slot move_from
move_to closure` and `Project_value_slot_from project_from slot closure`;
`static_const` gains `Static_const_closure_of_set slot closure_symbols
function_decls value_slots` (one `Bind_symbol` for each symbol of a
static set); `value` gains `Value_closure_of_set slot function_decls
value_slots`; `statically_allocated_value` gains `Static_closure_of_set`.
`closure_of` keeps its type, so `call_function` and `step` do not
change: `my_closure` is bound to the callee, which is the closure at
that function's slot. A `Let` of several closures is a derived form
(`let_closures`): the first closure is made, the others are projected
from it; a static set is `bind_closures`. `expr` and `static_binding`
get no constructor. Today's forms stay, as a set of one function whose
slot has no name, and are to be deleted by a later, small request
("C3b", an epoch of its own; the request says what it needs first).
The terms can write sets the compiler cannot make; the machine's
behaviour on them is a choice, said in the header of
`FlambdaSemanticsSpec.v`, and `well_formed_unit` refuses them.

## Done after the epoch

- The request, section 2, on R2's word: it says exactly what the
  machine checks of a call (the number of arguments, and for a direct
  call the code named; kinds and arities are C2's work).
- The integrator merged the `CR` at `call_function` with its own: one
  block, C3's item first.
- One more discrepancy with the compiler is recorded, C3-8: the model
  can write a value slot twice in a set and the compiler cannot (its
  value slots are a map). The condition is the integrator's row 7f.
- The invariant on values (request, section 8; R2), as leaf work in
  `FlambdaClosuresSpec.v` and `FlambdaClosuresProofs.v`. Eight
  statements, proved; nothing admitted, no axiom.
  - `value_valid`: every closure of a set in the value is at a function
    slot of its set, whose function slots are distinct and whose
    functions have each their own code, through value slots and blocks.
    `allocated_valid`: the same of what a symbol is bound to, and a
    static set names a symbol for each of its function slots. Neither
    asks that code or symbols are bound.
  - `well_formed_values_valid_statement` and
    `well_formed_exit_valid_statement`: every state of the run of a
    well-formed unit holds valid values only (`state_valid`, which is
    `state_values_all` of the two predicates), and the run ends with
    valid values. Proved with `step_values_all` and the invariant on
    terms (`sets_inv_step`).
  - `well_formed_closure_slot_statement`: a closure that such a run
    calls is at the only slot of its set that has the code called.
  - `call_binds_my_closure_statement`: a call binds `my_closure` to the
    closure called, where `my_closure` is not also a parameter of the
    code. `well_formed_unit` does not ask that yet (R2: a parameter of
    the same name hides it), so that `my_closure` is at the slot of the
    code that runs holds of code whose binders are distinct, and of
    every well-formed unit only once that is a condition of
    well-formedness.
  - `closure_in_set_valid_statement`,
    `project_function_slot_valid_statement` (the projection of a
    function slot has a value whenever the set has the slot asked for,
    from a symbol too), `eval_named_valid_statement` and
    `eval_static_const_valid_statement` (the case of a primitive by
    C1's law `eval_prim_preserves_statement`).
  It is on the integration branch, over N1's traversal of where a
  state holds values.

## Decided overnight

For the human to review. Each is a choice of the request on partial
applications (its section 7), taken so that the work could go on; none
is applied to the integration branch yet.

1. Which calls are generic applications. Options: every call whose
   arities pass the compiler's test, as Simplify treats them; or
   indirect calls only, a direct call with another number of arguments
   than parameters staying undefined. Chosen: indirect only. Why: the
   backend stops on such a direct call and no term of the compiler has
   one, and undefined is the side on which every rewrite is a
   refinement. To change: two lines of `call_function_returning`.
2. One `Indirect` call kind for the compiler's two. Options: keep one;
   or add a known-arity kind that is exact like `Direct`. Chosen: one,
   with a review comment. Why: the compiler makes known-arity calls
   exact, so the two agree on its terms. To change: a constructor of
   `call_kind`, a case in each match on it and in the converter.
3. What a partial application is. Options: a value of its own, which
   is not a closure of code; or nothing new, the machine making a
   closure of wrapper code as Simplify does. Chosen: a value of its
   own. Why: the machine cannot make new code, and Simplify's wrapper
   depends on which arguments are variables. Cost: a partial
   application of a known function runs the same before and after
   Simplify but does not validate until values are compared up to a
   relation. To change: that relation, which other work needs too.
4. When a partial application reaches its return continuation.
   Options: in the step of the call, which makes `apply_cont_value`
   recursive on the continuation; or in a step of its own through a
   state that the machine makes up, with names of its own. Chosen: in
   the step of the call. Why: the machine then makes up no name, and
   its steps commute with renaming as the work on names needs. Cost:
   the proofs about a call get an induction on the continuation. To
   change: one definition, and those proofs become shorter.

## Agreed with other streams

- T1 (types): `type_satisfied` takes the static environment and reads a
  closure only through `closure_of`, `closure_in_set` and
  `project_function_slot`, never by matching on a constructor.
  `function_slot : Type := positive`, under that name. T1's option (a):
  the semantics reads today's unnamed forms as the closure at
  `unnamed_function_slot := 1` of a set with that one function, so
  `closure_in_set` is defined wherever `closure_of` is. T1 defines the
  two observations with the same names and argument orders until the C3
  epoch, which then deletes T1's copies. The unnamed forms are meant to
  be retired later; nothing is to depend on the constant.
- C2 (kinds): `Let` will carry a kind, `Handler` and `Code` arities,
  `apply_expr` two arities, and `call_function` two more arguments that
  it compares with the code's. C3 changes neither `code` nor
  `call_function`. Fallout of C3 on C2's files: a case of `kind_of_named`
  for each new form of `named`, a case of `kind_of_value` and of the
  well-kinded-value predicate for the new value forms. Value slots get
  their kinds from a table given to the checker, not from the term. The
  checker does not ask for code ids in scope. The structural conditions
  on a set were to be a conjunct of that checker. They are not: C0 asked
  for them in `well_formed_unit`, since they are about static bindings
  and real units may fail a check of kinds. So C3 does not wait for C2.
- C1 (primitives), landed: `Project_value_slot` stays in `named`, so
  the new projections are there. The value constructors, `closure_in_set`
  and the two projections are in `FlambdaValueSpec.v`; their statements
  in `FlambdaSemanticsSpec.v`. Nothing of C1's matches on
  `Value_closure`; closures are read through `closure_of`, and C1's
  files build with no edit but for one pattern of
  `FlambdaPrimitiveProofs.v`. `eval_prim_avoids` is a lemma whose
  proof needed no edit. `Phys_equal`, when it comes, will have no value on
  closures.
- `Project_value_slot_from` was added after the first exchange. C2 and
  T1 have been told: for C2 it is one more case of `kind_of_named` (the
  kind its table gives the value slot); for T1 it is the observation
  `project_value_slot`, which is `closure_in_set` and a `lookup`. It
  does not touch anything of C1's.
- T1 again, after a review of its types: `closure_in_set_slot_statement`
  (a closure is at one of the function slots of its set) is stated and
  proved in `FlambdaSemanticsSpec.v` under the name T1 uses, with no
  premise, for a value and for a symbol. T1 carries no premise for it.
- N1 (names), on the two invariants of a state. The line is between
  names and values. N1 writes the scope invariant (`state_in_scope`:
  the variables and continuations of the expression and of every
  continuation closure are in scope, and all the code of the static
  environment is closed); it says nothing of any value. C3 writes the
  invariant on values. No value holds a variable or a continuation.
  N1 also writes the traversal both need, once: `state_values_all P Q
  s`, with `P : static_env -> value -> Prop` for the values of the
  variable environment and of the environments that continuation
  closures captured, recursively, and `Q : static_env ->
  statically_allocated_value -> Prop` for what each symbol is bound
  to. Its statement takes the client's obligations as hypotheses about
  the state at hand (the value a `Let` makes; what a `Let_static`
  binds; the values that an `Apply` or an `Apply_cont` reads), and
  gives `state_values_all P Q` of the next state, or `P` of the
  arguments of an exit. The condition that every symbol mentioned is
  bound is a third client. Neither invariant assumes that the code id
  of a closure is bound: that is not ruled (the `CR` at
  `call_function`), and false of deleted code as the model stands.
- The integrator, on 7f: distinct value slots become a condition of
  well-formedness (the compiler has it by type; C3-8), added by the
  integrator outside `set_well_formed` and `static_set_whole`, so that
  the proofs of `FlambdaClosuresProofs.v` move by a split or two.
