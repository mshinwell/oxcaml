## The design, in one paragraph

Constructors are added and none is changed. `named` gains
`Closure_of_set slot function_decls value_slots` (the closure at one
function slot of a newly made set), `Project_function_slot move_from
move_to closure` and `Project_value_slot_from project_from slot closure`;
`static_const` gains `Static_const_closure_of_set slot closure_symbols
function_decls value_slots` (one `Bind_symbol` for each symbol of a
static set); `value` gains `Value_closure_of_set slot function_decls
value_slots`; `statically_allocated_value` gains `Static_closure_of_set`.
`closure_of` keeps its type, so `call_function` and `step` do not
change: `my_closure` is bound to the callee, which is the closure at
that function's slot. A `Let` of several closures is a derived form
(`let_closures`): the first closure is made, the others are projected
from it; a static set is `bind_closures`. `expr` and `static_binding`
get no constructor. Today's forms stay, as a set of one function whose
slot has no name, and are to be deleted by a later, small request
("C3b", an epoch of its own; the request says what it needs first).
The terms can write sets the compiler cannot make; the machine's
behaviour on them is a choice, said in the header of
`FlambdaSemanticsSpec.v`, and `well_formed_unit` refuses them.

    slot of its set, whose function slots are distinct and whose

    `well_formed_exit_valid_statement`: every state of the run of a
    well-formed unit holds valid values only (`state_valid`, which is

    terms (`sets_inv_step`).

    calls is at the only slot of its set that has the code called.
  - `call_binds_my_closure_statement`: a call binds `my_closure` to the
    closure called, where `my_closure` is not also a parameter of the
    code (R2: a parameter of the same name hides it). Since
    `well_formed_unit` asks that the binders of code are distinct:
    `well_formed_code_binders_statement` (the code that the run of a
    well-formed unit binds has distinct binders) and
    `well_formed_call_binds_my_closure_statement` (a call in such a run
    binds `my_closure` to the closure called, with no premise on the
    code).

    `project_function_slot_valid_statement` (the projection of a
    function slot has a value whenever the set has the slot asked for,
    from a symbol too), `eval_named_valid_statement` and
    `eval_static_const_valid_statement` (the case of a primitive by

## Decided overnight

For the human to review. The first six are choices of the request on
partial applications (its section 7), taken so that the work could go
on; they are on the integration branch with that series. Decisions 7
to 9, on tupled functions, are under "Later"; the first series on
tupled functions is made by them.

1. Which calls are generic applications. Options: every call, as
   Simplify treats them once it knows the callee; or indirect calls
   only, a direct call with another number of arguments than parameters
   staying undefined. First chosen: indirect only. Changed while the
   series was made to: every call. Why: with a direct call exact, "an
   indirect call of a known closure is a direct call of its code" is
   true of full calls only, and that is three statements, one of them
   the canonicalisation by aliases that the validator runs with no
   arity of the code to test. The cost: the machine gives a meaning to
   direct calls that the backend refuses (discrepancy C3-9; a review
   comment at `shape_of_closure_call`). To change back: one line of
   `shape_of_closure_call`, and a premise on the number of arguments in
   those three statements.
2. One `Indirect` call kind for the compiler's two. Options: keep one;
   or add a known-arity kind that is exact like `Direct`. Chosen: one,
   with a review comment. Why: the compiler makes known-arity calls
   exact, so the two agree on its terms. To change: a constructor of
   `call_kind`, a case in each match on it and in the converter.
3. What a partial application is. Options: a value of its own, which
   is not a closure of code; or nothing new, the machine making a
   closure of wrapper code as Simplify does. Chosen: a value of its
   own. Why: the machine cannot make new code, and Simplify's wrapper
   depends on which arguments are variables. Cost: a partial
   application of a known function runs the same before and after
   Simplify but does not validate until values are compared up to a
   relation. To change: that relation, which other work needs too.
4. When a partial application reaches its return continuation.
   Options: in the step of the call, which makes `apply_cont_value`
   recursive on the continuation; or in a step of its own through a
   state that the machine makes up, with names of its own. Chosen: in
   the step of the call. Why: the machine then makes up no name, and
   its steps commute with renaming as the work on names needs. Cost:
   the proofs about a call get an induction on the continuation. To
   change: one definition, and those proofs become shorter.

5. A call that gives a partial application no argument. Options:
   undefined; or the partial application again. Chosen: undefined. Why:
   the compiler stops on a call with no argument of code that has
   parameters, and its partial applications are closures of code with
   the parameters that are left. To change: one line of
   `shape_of_call`.
6. Inlining and the number of arguments. `inlinable` now asks that the
   call has as many arguments as the code has parameters, counted by
   parameter, beside as many values as variables. Why: with a parameter
   that is an unboxed product of nothing the two differ, and such a
   call is a partial application or an over-application. No other
   option keeps `inline_statement` true.

Not choices, but changed after the request was first reviewed, and to
be known:

- The kinds of a call's own arguments (R2's finding). An indirect call
  of a partial application is the call of the closure it keeps with
  all the arguments, and that call tests the kinds of all of them
  together. A partial application that no call made, one whose kept
  arguments are not of the kinds of the arity it keeps, could hide a
  mismatch of the new arguments in that test. `shape_of_call` now
  tests the call's own arguments against its own arity first, as
  Simplify does of every call. The statements:
  `apply_partial_application_kinds_statement` and, for the example,
  `malformed_partial_application_statement`.
- Exceptions in an over-application. What is left of the application
  keeps the exception continuation of the call with the extra
  arguments already evaluated, since nothing is left to evaluate them
  in. The term that splits an over-application names the same
  continuation with the same extra arguments in both calls, so the two
  agree (`over_application_split_statement` asks that the variable of
  the handler is not among those arguments).
- The handler of the term that splits an over-application has one
  parameter of kind `Value` and is not an exception handler: the
  statement fixes its metadata (R2).
- The two constructors (`Value_partial_application` and
  `Over_application`) were first a commit of their own; they are now
  in the commit that changes the calls, so that the proofs about a
  continuation are repaired once over the epoch of exceptions.
