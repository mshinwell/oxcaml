## The design, in one paragraph

Constructors are added and none is changed. `named` gains
`Closure_of_set slot function_decls value_slots` (the closure at one
function slot of a newly made set), `Project_function_slot move_from
move_to closure` and `Project_value_slot_from project_from slot closure`;
`static_const` gains `Static_const_closure_of_set slot closure_symbols
function_decls value_slots` (one `Bind_symbol` for each symbol of a
static set); `value` gains `Value_closure_of_set slot function_decls
value_slots`; `statically_allocated_value` gains `Static_closure_of_set`.
`closure_of` keeps its type, so `call_function` and `step` do not
change: `my_closure` is bound to the callee, which is the closure at
that function's slot. A `Let` of several closures is a derived form
(`let_closures`): the first closure is made, the others are projected
from it; a static set is `bind_closures`. `expr` and `static_binding`
get no constructor. Today's forms stay, as a set of one function whose
slot has no name, and are to be deleted by a later, small request
("C3b", an epoch of its own; the request says what it needs first).
The terms can write sets the compiler cannot make; the machine's
behaviour on them is a choice, said in the header of
`FlambdaSemanticsSpec.v`, and `well_formed_unit` refuses them.

## Agreed with other streams

- T1 (types): `type_satisfied` takes the static environment and reads a
  closure only through `closure_of`, `closure_in_set` and
  `project_function_slot`, never by matching on a constructor.
  `function_slot : Type := positive`, under that name. T1's option (a):
  the semantics reads today's unnamed forms as the closure at
  `unnamed_function_slot := 1` of a set with that one function, so
  `closure_in_set` is defined wherever `closure_of` is. T1 defines the
  two observations with the same names and argument orders until the C3
  epoch, which then deletes T1's copies. The unnamed forms are meant to
  be retired later; nothing is to depend on the constant.
- C2 (kinds): `Let` will carry a kind, `Handler` and `Code` arities,
  `apply_expr` two arities, and `call_function` two more arguments that
  it compares with the code's. C3 changes neither `code` nor
  `call_function`. Fallout of C3 on C2's files: a case of `kind_of_named`
  for each new form of `named`, a case of `kind_of_value` and of the
  well-kinded-value predicate for the new value forms. Value slots get
  their kinds from a table given to the checker, not from the term. The
  checker does not ask for code ids in scope. The structural conditions
  on a set were to be a conjunct of that checker. They are not: C0 asked
  for them in `well_formed_unit`, since they are about static bindings
  and real units may fail a check of kinds. So C3 does not wait for C2.
- C1 (primitives), landed: `Project_value_slot` stays in `named`, so
  the new projections are there. The value constructors, `closure_in_set`
  and the two projections are in `FlambdaValueSpec.v`; their statements
  in `FlambdaSemanticsSpec.v`. Nothing of C1's matches on
  `Value_closure`; closures are read through `closure_of`, and C1's
  files build with no edit but for one pattern of
  `FlambdaPrimitiveProofs.v`. `eval_prim_avoids` is a lemma whose
  proof needed no edit. `Phys_equal`, when it comes, will have no value on
  closures.
- `Project_value_slot_from` was added after the first exchange. C2 and
  T1 have been told: for C2 it is one more case of `kind_of_named` (the
  kind its table gives the value slot); for T1 it is the observation
  `project_value_slot`, which is `closure_in_set` and a `lookup`. It
  does not touch anything of C1's.
- T1 again, after a review of its types: `closure_in_set_slot_statement`
  (a closure is at one of the function slots of its set) is stated and
  proved in `FlambdaSemanticsSpec.v` under the name T1 uses, with no
  premise, for a value and for a symbol. T1 carries no premise for it.
