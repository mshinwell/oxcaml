## Decided overnight (2026-11-11 and 12), for the human

1. **Regions** (D37, decided by the orchestrator for the human):
   dropped, local allocations converted as heap ones. Widened on
   2026-11-12 to the regions around a `try` (`Begin_try_region`,
   `End_try_region`), which every handler of the source has: dropped
   in the same way, the assumption being also that nothing allocated
   in a region that a raise left open is used once the handler has
   ended it. The ledger and the header of the tool say so. Cost of
   changing: every unit with a `try`, and `match_variant_local.ml`, is
   "not checked".
2. **Tupled functions.** Options: refuse all code marked tupled; refuse
   only a unit that also has a call that is not direct; model the mark.
   Chosen: the second, as a direct call gives the components and is
   run faithfully (agreed with C2). Since replaced by the third: C3
   has put the mark in the model, where every call gives tupled code
   its tuple, and the tool refuses only the calls that give it the
   components.
3. **Which calls the validator leaves alone.** The tool tries the code
   the term after still calls directly with the recursive code added,
   then the recursive code alone. Cost of changing: a few lines of the
   test tool; nothing proved depends on it.
4. **Which primitives `share_known_primitives` shares.** Those that
   compute a number from numbers or look at a value without reading
   memory that can change; not loads, not allocations. The compiler
   shares immutable allocations too (the file has a comment for the
   human on it). Cost of changing: the list `shareable`.
5. **A load marked mutable of a known block**: left as it is by
   `load_known_blocks`, as Simplify leaves it.
6. **Renaming binders apart, and the statements that the validator
   commutes with renaming** (N3's `FlambdaValidatorEquivarianceSpec.v`).
   `rename_apart` makes names, so a round commutes with a renaming
   only up to the names it makes. The orchestrator ruled: no statement
   is removed with its replacement owed. So the wiring of
   `rename_apart` lands with N3's statements for one round, for
   `normalise_before` and for the verdict (the validation answers the
   same on a pair and on the pair renamed, where the code of the term
   before is closed), and N2's statements that each rewrite of a round
   keeps scope.

## What "validated" rests on, for a unit from OCaml

Beyond the trust ledger (the conversion to the model, the parser):

- the printing of `-drawfexpr`: the term validated is the one the
  parser reads back. It is the term the compiler simplifies only as far
  as printing and parsing lose nothing, and they do lose something: the
  kinds of the fields of a `Make_block` (read back as `any_value`) and
  the arities of calls (discrepancies V2-2, C2-5, R2-12). X5
  compared the term in the compiler's memory with the term read back
  for each unit: the subkind of the result of an application and
  the mark `[cold]` of a continuation handler are lost as well, and
  Simplify reads each (the README of the corpus has the places).
  With these the tool's Simplify knows less than the compiler's;
- the same printing where it says more than the compiler's term: a
  value that may be null is read as never null wherever the text
  writes its kind (discrepancy T4-13; found by T4). As far as this
  loss goes, the model's term before is the compiler's, as the
  conversion drops these kinds; the term after can differ where
  Simplify used the kind. The 13 units of the corpus that have such
  a kind are counted apart: the tool's verdict on each is
  "validated", and the row says that nothing in the tree shows that
  its term after is the compiler's, not that it is not. X5 has
  since given the check of the tool the two terms of the compiler's
  own run, for the 259 units that the corpus had at ba85db2822,
  converted with one change that the tool has not got (the kinds of
  the fields of a `Make_block` dropped). For each of the 13 the two
  terms after as printed are the same up to names; over the 259,
  the check prints of the compiler's pair what it prints of the
  tool's for 252, the conversion refuses 5 in both ways, and for 2
  the compiler's term after is not well-formed (discrepancy X5-9).
  These are answers with that changed conversion and a comparison
  of texts: nothing is claimed of dropping the kinds, and the
  comparison does not see what the text does not write. The README
  of the corpus has the measure ("What a validation does not say"),
  which nothing in the tree makes;
- how a unit is found to have such a kind, which is looked for
  before a unit enters the corpus. The raw print of the compiler
  (`-drawflambda`) writes a kind of values that may be null with a
  question mark. It is read for the places where the fexpr text
  writes a kind and so loses the mark: the fields of a block shape, a
  kind that has a subkind, and an arity of results of more than one
  component. A kind that stands alone with no subkind is left out by
  the text and is read back right; the arities of the parameters of
  code and of the arguments of a call, and the shape of a
  `Make_block`, are put aside, as the text does not write them. A
  unit with no such place is counted as the tool says, and a unit
  with one is counted apart. For each of the 325 units that the
  corpus had on 2026-11-13 this count was compared with a second
  one: the number of kinds marked in the fexpr text by a copy of the
  compiler whose printer was changed to mark such a kind wherever it
  writes one (T4's candidate repair of T4-13, which is not in the
  tree). The two give the same thirteen units, with the same
  numbers. One difference between the two was seen, on
  a unit that the tool does not read (`pairs/cycle.ml`): the changed
  printer marks the arities of a call of C, and the reading of the
  raw print does not count them;
- the modes of the parameters of code, which the text has not got.
  The reader gives every parameter the mode heap, and Simplify on a
  term read so can take a parameter that may be on the stack for a
  block of the heap, and return it where the compiler copies it to
  the heap (discrepancy X5-11; found by X5, on a unit that is not
  in the tree). From stage 100 the tool gives every parameter of
  every piece of code that the unit binds the least that the
  compiler can say of where a value is
  (`Alloc_mode.For_types.unknown ()`: heap or stack, and heap in a
  compiler configured without stack allocation), before its
  Simplify runs (`with_unknown_param_modes`,
  tests/tools/flsemantics.ml): no verdict rests on the reader's
  mode heap for such a parameter, and no unit is counted apart for
  it. That is of these modes only: the other defaults of the reader
  stay, and code read from the `.cmx` file of another unit has the
  modes that the compiler wrote. Where the compiler allocates on
  the stack, the modes then tell the tool's Simplify less than
  those of the compiler's term tell the compiler's, of a parameter
  that the compiler's term says is on the heap: a distance, as the
  losses of the first item. How it was
  looked for: the raw print of the compiler (`-drawflambda`) writes
  `param_modes` for each piece of code. Of the 331 units that the
  corpus had on 2026-11-13, 20 have a parameter whose mode is not
  heap (each is heap or stack; no source says `local_`, the
  compiler infers the mode), and 4 of the 20 are among the 13 of
  T4-13; the README of the corpus names them. With the change no
  expected file of the corpus has another verdict or another count
  of steps (two have other names of variables in the message of a
  primitive that the model has not got, as the unit is built again
  with fresh names for what it binds), and the 840 generated units
  of `census/`, run before and after, have the verdicts they had.
  The model erases the regions of allocation and their lifetimes:
  no verdict, plain or counted apart, says that a block which is
  returned is still alive;
- that the tool runs Simplify as the compiler would: the tool uses the
  default flags, and so does the command that makes the term. It does
  not where Simplify reads a mark of code that the printed term has
  not got: a functor, `[@cold]`, opaque code, the modes of
  parameters. One case is known: for code with no inlining
  attribute, the decision made at the declaration compares the size
  of a functor with the thresholds for functors, and a functor no
  larger than `small_functor_size` is to be inlined; the tool's
  Simplify, to which the functor is a function, compares it with the
  thresholds for functions and may leave the call (discrepancy V2-6;
  found by T4);
- what the conversion leaves out: depths, regions (the ledger has the
  entry).
