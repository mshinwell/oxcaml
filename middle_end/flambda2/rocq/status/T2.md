# T2, the typing environment: status

Branch `flambda2-rocq/T2-env`, on T3's `flambda2-rocq/T3-aliases`, which
is on the integration branch. Files, all in
`middle_end/flambda2/types/rocq/`:

- `FlambdaBindingTime.v`: binding times and name modes. Written by T3
  as the first commit of its branch, owned by T2.
- `FlambdaTypingEnv.v`: the environment and its functions, in modules
  with the compiler's names (`Typing_env_level`, `Cached_level`,
  `Typing_env`). Definitions only; it extracts to plain OCaml (tried on
  the side). Its header says, field by field, what the model has of
  `Typing_env.t` and every difference.
- `FlambdaTypingEnvSpec.v`, `FlambdaTypingEnvProofs.v`: what satisfies
  an environment and what looking a name up gives. 32 statements.
- `FlambdaTypingEnvExamplesSpec.v`, `FlambdaTypingEnvExamplesProofs.v`:
  the environment that Simplify builds for a small term, the same in
  the body of a closure, the handler of a continuation after a join, a
  symbol, poison; with machine environments that do and do not satisfy
  each. 24 statements.

- `FlambdaTypingEnvInvariantSpec.v`,
  `FlambdaTypingEnvInvariantProofs.v`: the invariant of an environment,
  as a test and as conditions, with where the compiler has each; what
  it gives to `cut` and to the aliases; that the functions keep it. 21
  statements.

- `FlambdaTypingEnvOperationsSpec.v`,
  `FlambdaTypingEnvOperationsProofs.v`: what the functions that build
  an environment do to what satisfies it. 16 statements.

`FlambdaEnvAliases.v`, `FlambdaEnvAliasesSpec.v`,
`FlambdaEnvAliasesProofs.v` and T3's files on the invariant and the
renaming of the aliases are T3's, and are on this branch as T3's own
commits.

## Done

First merge request: the environment, what satisfies it, lookup.

- The definitions (`FlambdaTypingEnv.v`): levels, the environment,
  `find`, `mem`, `add_variable_definition`, `add_symbol_definition`,
  `add_definition`, `replace_equation`, `add_alias`, `increment_scope`,
  `cut`, `closure_env`, `type_simple_in_term_exn`,
  `get_canonical_simple_exn` and the functions around them.
- What satisfies an environment, in two layers: a valuation, which may
  give a value to any variable the environment knows, and the machine,
  which binds the variables in scope and agrees on them with a
  valuation that satisfies the environment. The header of the Spec says
  why, and what is asked of a name with no value at run time, of
  symbols, of code and of poison.
- Valuations are partial: a variable that a join made existential
  stands for nothing in a run through a use that does not define it
  (discrepancy T2-6). Nothing is asked of a name with no value, so a
  statement about a name that is not reached through a value in hand
  needs the premise that the name has one (`example_absent_env`: a
  name of type bottom in an environment that is not bottom, which
  `Meet_env` builds for the binary join).
- `typing_env_satisfied_but exempt statics valuation tenv` is the one
  definition; of an exempt name only the kind is asked. Named cases:
  - `typing_env_satisfied_strictly` (no name exempt) and
    `env_satisfies_strictly`: for the statements about types (meet,
    join, the provers) and for Simplify up to variant unboxing;
  - `typing_env_satisfied` and `env_satisfies` (D26, the orchestrator's
    ruling; two `CR mshinwell`): exempt are the names that hold poison
    and, since the ruling was revised and then amended (`Is_int` and
    `Get_tag` are never true of a scrutinee that holds poison; `Is_null`
    relates poison of kind value to 0), the names whose type is an
    `Is_int` or a `Get_tag` relation on a name that holds poison
    (`exempt_by_poison`, `relation_on_poison`;
    `example_relation_env_poison`). Only `find_not_poison` follows from
    it: with an exempt name an alias may not be replaced by the type of
    the name (`example_env_poison_alias_type`). The header's sentence
    that under strict satisfaction a statement that reads an `Is_int`
    or a `Get_tag` relation has no case of poison is true once
    `relation_holds` of `FlambdaTypeMeaningSpec.v` has no poison clause
    for the two; on the integration branch it still has them (T1's
    change is on its branch), and the header says so.
- Statements: how the notions compare (`satisfied_but_weaken`,
  `satisfied_strictly_satisfied`, `satisfied_no_poison_strictly`,
  `env_satisfies_strictly_env_satisfies`); what satisfaction depends on
  (`satisfied_but_coincide`, `typing_env_satisfied_coincide`,
  `env_satisfies_coincide`, `env_satisfies_strictly_coincide`); lookup
  (`find_satisfied`, `find_satisfied_strictly`, `alias_has_type_found`,
  `find_not_poison`, `find_kind`, `find_cases`, `mem_find`,
  `in_scope_in_terms_bound`, `find_variable_in_terms_strictly`,
  `find_variable_in_terms`, `find_symbol_in_terms`); canonical
  elements, for any exempt names
  (`canonical_ignoring_name_mode_satisfied`,
  `get_canonical_simple_satisfied`,
  `get_alias_then_canonical_simple_satisfied`,
  `type_simple_in_term_satisfied`, `type_simple_in_term_canonical`).
  None has a premise on the environment.

## Second request: done so far

The first request ends at the commit "T2: lines for the shared lists"
that lists five files; the second request is the series above it.

The invariant (`FlambdaTypingEnvInvariantSpec.v`):

- `typing_env_well_formed : Typing_env.t -> bool`, the test of fifteen
  conditions, each also a proposition
  (`typing_env_well_formed_iff`): of the names and their types
  (`binding_times_bounded`, `binding_times_in_range`,
  `binding_times_distinct`, `types_closed`, `symbols_defined`), of the
  levels (`levels_pairwise_disjoint`, `defined_variables_bound`,
  `levels_indexed`, `level_binding_times_recorded`,
  `level_binding_times_in_range`, `scopes_decreasing`), of the aliases
  (T3's `aliases_consistent` and `name_modes_recorded`, `aliases_known`,
  `canonical_names_concrete`). The header says for each where the
  compiler establishes or checks it, and each condition where the model
  is stricter than the compiler has a comment (D32).
- The index of a level (a finding of the review: nothing was asked of
  `binding_times` of a level against its `defined_vars`).
  `levels_indexed`: the variables that a level has by binding time are
  those that it defines (`level_indexed`, `indexed_at`; what
  `Typing_env_level.create` checks under invariant checks and
  `fold_on_defined_vars` relies on always).
  `level_binding_times_recorded`: a variable that a level has at a
  binding time has that binding time in the environment (by
  construction; nothing checks it). Not asked: that no variable is
  twice among those of one binding time (the compiler has a set there,
  the model a list).
- Kinds. One condition speaks of kinds, `defined_variables_bound`: the
  kind that a level has for a variable is the kind of the type that the
  environment has for it. It is of two records of one definition, and
  the compiler keeps it by checks that no flag guards
  (`add_variable_definition`; `Typing_env.find` with a kind in the
  callers of `replace_equation`, which itself checks nothing:
  discrepancy T2-8). The kinds of the aliases inside types are not part
  of the invariant and will not be (D32 is no licence for kinds): they
  are to be a separate premise, `typing_env_kinded` (below, "Next").
- `levels_agree` (the equation of the latest level for a name is the
  type the environment has for it) is a proposition only: it compares
  types, and there is no test of equality of types on this base. So
  `typing_env_invariant tenv := typing_env_well_formed tenv = true ∧
  levels_agree tenv`. To be folded into the test when T1's `type_eqb`
  is under this branch.
- What it gives: `cut_defined`, `cut_equations_found`,
  `cut_defined_variables_found`, `cut_indexed` (the level that `cut`
  answers has its index, and its variables are at the binding times of
  the environment), `well_formed_binding_times_distinct` (for T3's
  order of the aliases), `well_formed_mentioned_known`, `find_closed`
  (the variables of a type found are bound; T4's, as is `find_cases`);
  `levels_disjoint_b_iff`, `concat_defined`, `level_indexed_b_iff`,
  `concat_indexed`.
- The functions keep it: `create_invariant`, `make_bottom_invariant`,
  `increment_scope_invariant`, `closure_env_invariant`,
  `add_symbol_definition_invariant`,
  `add_variable_definition_invariant` (the variable is not bound),
  `replace_equation_invariant` (the name is bound; the variables of the
  type are bound; the type has the kind of the one the name had; if it
  is an alias the name is not canonical; and it is not obviously
  unknown, or no level before the current one has an equation on the
  name: discrepancy T2-4), `add_alias_invariant` (the two are canonical
  and bound), `add_alias_defined`.

What the functions do to satisfaction
(`FlambdaTypingEnvOperationsSpec.v`), each for
`typing_env_satisfied_but` with any names exempt, the same before and
after, so for strict satisfaction:

- `increment_scope_satisfied`, `closure_env_satisfied`,
  `add_symbol_definition_satisfied` (the same valuations before and
  after), `increment_scope_env_satisfies_strictly`;
- `add_variable_definition_satisfied` (the valuation as it is, if the
  value it has for the variable, if any, is of the kind),
  `add_variable_definition_satisfied_bind` (the variable bound to any
  value of the kind, if the environment does not mention it),
  `well_formed_not_mentioned` (so of a variable that is not bound in a
  well-formed environment), `add_variable_definition_satisfied_inv`;
- `replace_equation_satisfied` (the value of the name, if any, has the

- `add_alias_satisfied` (from T3's `add_respected`), `add_alias_bottom`
  (no valuation gives two different constants one value);
- `satisfied_but_statics_extend`,
  `env_satisfies_strictly_statics_extend`,
  `env_satisfies_strictly_bind`, `env_satisfies_bind` (the machine
  binds a variable that the environment does not know).

For equations given by a meet the statement is T4's

## Open

- An alternative to D26, from T4: with partial valuations the exemption
  of poison could go, if the valuation were allowed to give no value to
  a variable in scope. The handler of an unboxed variant is then
  satisfied strictly by the valuation that leaves out the parameters of
  the inactive case, and the statements about types apply there. It is
  implied by D26 as stated (drop the names whose types fail, and
  repeatedly those that depend on them). What it costs: what must be
  left out is more than the poison (the `Is_int` and tag parameters
  that hold 0; a block built from the poison), so the machine-level
  statement has to say which variables in scope have values, and a
  rewrite that uses a fact about a variable needs that premise. Not
  taken; reported to the orchestrator.
