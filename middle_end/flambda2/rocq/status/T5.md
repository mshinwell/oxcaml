## Changes to the contract since the first version

- The premise that each use entails the source is gone: an
  environment made by adding an equation does not entail the one it
  was made from (R1's example; T7-4). `join_admits_use` asks, for each
  valuation, that it satisfy the source as well as the use; in the
  machine, `use_and_source_satisfied`.
- Agreement is exact: a variable that the use or the source knows has
  in the witness what it had, the same value or none
  (`agrees_on_known`). For a while it was weaker (a variable with no
  value could get one, for the case of a name of type bottom at a
  use); R1 then showed T4 that a caller cannot supply "the valuation
  satisfies the source" after such a step. Agreed with T4: exact
  agreement, and `no_bottom_types` asked of the inputs of every join
  and guaranteed of its target.
- Kinds (the orchestrator's ruling): the transcription answers what the
  compiler answers; `uses_kinded` is a premise of the contract and
  `type_kinded` of the join of types (`aliases_with_kinds`), with a
  note for the human at `typing_env_kinded`. Discrepancy T5-9.
- Each index is given once to the callbacks (`join_args_distinct`).
- From the review of the interface: every one of the four callback
  contracts has the premise `joined_envs_kinded` (it is not part of
  `state_valid`: the inputs do not change in a join); the header says
  that the target is not promised to be kinded, that an unforced
  variable may be left without a value, that a relation is never true
  of a scrutinee that holds poison (D26 as revised; T1's
  `relation_holds` on my base still has the clauses for poison), and
  that an imported type keeps the values that have it and may gain
  some.
- Kinds out (T4's request, and the review): `join_keeps_kinded` (the
  target is kinded if the source is and the uses have the source's
  names at the source's kinds), a statement beside the contract. For
  it the interface between the halves has the reading
  `kind_in_target_env` in place of `exists_in_target_env`, a second
  predicate `state_kinded`, and a kinds clause in each of the four
  contracts (`type_kinded_in_target`; the type joined has the kind of
  the types given; a simple joined at a kind other than value is not
  a symbol).
- Names with no value (T5-10; the orchestrator's ruling): the
  contract stays strict (`sound_join_of_environments`, what the meet
  assumes). What is to be proved of the compiler's join is
  `sound_join_where_values_are_read`: the same for the runs that
  satisfy `scrutinees_have_values` (for every relation of the target,
  the scrutinee has a value where the result has one; a note for the
  human there: nothing in the compiler establishes it),
  `joined_variables_have_values` and
  `imported_variables_have_values` (R1's case, through T4: the type
  joiner passes over a head of naked immediates that its relations
  reduce to nothing, and a type with one constant for only value makes
  the variable an alias of it). Proved:
  `sound_join_where_values_are_read_of_sound`.
- The instance (`FlambdaJoinEnvSpec.v`, `FlambdaJoinEnvProofs.v`,
  module `Witness`): the transcribed join, with stand-ins for the
  meet's environment and the join of types, has not the strict
  contract. Five statements proved:
  `witness_join_of_types_upper_bound`, `witness_inputs_well_formed`
  (against T2's `typing_env_invariant`), `witness_run_satisfies`,
  `witness_use_not_admitted`, `transcribed_join_not_strict`.
- X2 has shown T5-10 from source: a wrong result at run time with the
  n-way join and `-O3` (a `Get_tag` relation recovered on an older tag
  variable for a variable imported from one branch).
- Exact agreement is not provable of the transcription on every

  search for a program (not found; the two cases occur in compiled
  programs, and are harmless there by a reading of five channels).
  Can that reading be stated as an invariant under which three
  conditions suffice? As a predicate, yes: of an environment and a
  run, "a name that has an equation and no value is not the canonical
  element of a name that has one, and a type of a name that has a
  value mentions it only inside a case, or the extension of a case,
  that the value is not in". As something the present statements can
  use, no: an environment extension is satisfied only if each of its
  names has a value (the meaning that the owners of types kept), so
  the extension that the join hands to the meet is false on those
  runs whatever happens later, and the meet's statement for adding an
  extension starts from a true one. To drop the condition one of two
  things has to change: the meaning of an equation of an extension on
  a name with no value (to "nothing is said"), or the meet's
  statement, to one for extensions whose equations are true where
  their names have values, in environments that have the predicate
  above, which the meet would then have to be shown to keep. Both are
  for the owners of the meaning of types and of the meet.
