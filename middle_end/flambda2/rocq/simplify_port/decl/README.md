# decl/: the declarations of what the port of Simplify calls

Every `.v` file here is GENERATED by `tools/declgen` from the compiled
interfaces of the compiler. Do not edit one: change the generator and run it
again. `INDEX.tsv`, `ARITIES.tsv`, `NOT-DECLARED.tsv`,
`FUNCTOR-ARGUMENTS.tsv`, `VARIANTS.tsv`, `UPDATES.tsv`,
`DONOR-TOKENS.tsv` and `DONOR-ITEMS.tsv` are generated with them.
`ARITIES.tsv` has its own section below, and so have `UPDATES.tsv`,
`DONOR-TOKENS.tsv` and `DONOR-ITEMS.tsv`, before it. `VARIANTS.tsv` has
one row for each
variant that is an `Inductive` here: the type in OCaml, the number of its
parameters, all its constructors in order, and a note where a later type of
its module has a constructor of the same name (the strings of the type's
directive then say the type). No file of decl/ depends on it: it is for a
program that reads the extracted text.

One file for each compilation unit of OCaml that the 78 files of
`middle_end/flambda2/simplify/` use, named as the unit (`Downwards_acc.v`,
`Flambda.v`, `List.v`), and one for each file of Simplify itself (whole
interface). A sub-module of OCaml is a `Module` of the file. Each file begins
with the header of the interface that it follows, then names that file and
says which text of it was read (the section "What a file says that it was
made from"): no commit is named.
Two interfaces have no header (`backend/debug/dwarf/dwarf_flags/dwarf_flags.mli`
and `utils/target_system.mli`): their files say so in its place.
Four files have, under the header or under those words, a QUESTION FOR A
HUMAN: one comment that begins with the word `CR` and the name of who is
asked. They are those two files (which header should they have?) and
`Numeric_types.v` and `Rebuilt_expr__local.v` (see the next paragraph: who
is to be credited for what they have of the standard library?). The words
are rows of `tools/declgen/crs.ml` and are nowhere else: the generator
writes them, and that file says how a question is changed, added or taken
away. THE WORDS ARE WRITTEN BY HAND and name things of the file. So each
row says the same things once more as data: the file whose notice the file
of `decl/` carries, whether that file has one, and what the file of
`decl/` declares (all of it, or what it has of the standard library). The
generator compares this with what it is about to write, and if it is no
longer so it STOPS AND WRITES NO FILE: the words are then read again and
the row mended. What it does not compare: the other words of a question.
`tools/aliases.py`, `tools/declgen/check_realisations.py` and
`tools/declgen/compile_all.py`, which read these files line by line, leave
such a comment out: a comment whose first line begins with the mark of a
comment and then `CR`, whole, and nothing else.

THE STANDARD LIBRARY IS NOT READ FROM THIS TREE. The compiled interfaces
of `List`, `Option`, `Format` and the other units of the standard library
are those of the OCaml that compiled the build's first stage, found
through the load path that the build recorded; the tree's own `stdlib/`
is compiled later, by the tree's own compiler, in a format that the OCaml
which builds `tools/declgen` does not read. What is taken from them is
the names and the types of 247 declarations here (232 values and 15
types): 200 in the 18 files that are named after a unit of the library,
42 in `Numeric_types.v` (what its `Int32` and `Int64` include of the
library's) and 5 in `Rebuilt_expr__local.v` (an application of
`Hashtbl.Make`). The header of each of the 18 files is that of the tree's
own `stdlib/NAME.mli` (as is that of `Lazy.v`, which declares nothing);
the two other files are of the compiler's modules and keep their own
headers. The comment GENERATED of each of these 19 files says it: that
the module is the standard library's, that its names and types are read
from the compiled interface of that module in the library of the OCaml
that built the compiler (and which one, by its digest), and that the
header above the comment is that of the tree's file of the same name. The
comment before such a declaration
(one for a whole family
of a function of formats) names the library's file, without a line; the
words of the comment are not that file's text: they are the name and the
type as the generator prints them from the compiled interface (for a
type, the name only). `PROVENANCE.md`, last section, has the commands that count them
and what a comparison of the two libraries' interfaces found.

## To make them again

    cd middle_end/flambda2/rocq/simplify_port
    tools/declgen/run.sh BUILD_ROOT          # every file of Simplify
    python3 tools/declgen/compile_all.py     # Rocq, one process at a time;
                                             # then the modules given to functors
    python3 tools/declgen/check_realisations.py BUILD_ROOT   # OCaml

`BUILD_ROOT` is the `_build/default` of a build of the compiler from the
sources of the tree. It need not be a build of the whole compiler:
`tools/typedtrees.sh` makes, in a tree that is configured, the compiled
interfaces and the typed trees that the generator and `make` read, and
no more (its head says what it runs, and how its list of directories is
kept). If a build lacks something that is read, the generator stops and
names it ("What a file says that it was made from", below).

What the last one checks, and what it does not. For each realisation string
it writes one line of OCaml (the string as an expression; for a type, as the
type of an argument; for a constructor or a field of a mirrored type, a
pattern or a projection with its name), and OCaml type-checks the lines
against the compiled interfaces, with `-nolabels` and the libraries that the
build opens for Simplify. So a name that does not exist, a wrong number of
type parameters, or a closed function that does not type is refused. For a
tuple with labels it also checks that the two functions of the directive make
and take the type that the directive names. A module type has no directive,
so nothing of it is checked here. It does
NOT compare the type that OCaml gives a realisation with the signature that
the declaration has in Rocq: that is checked only where a ported file uses
the declaration, by the check of the extracted file. Left out, and counted
apart in what it prints: the constructor functions of private types (OCaml
makes no value of such a type outside its module; the port must not build
one); what is declared of a module local to a file (`FILE__local.v`) when
that module is inside another module of its file, or when its definition,
copied from the file, does not compile apart from it.

`BUILD_ROOT` is the `_build/default` of a dune build of the compiler FROM
THE SOURCES OF THIS TREE (its `.cmt` and `.cmi` files are read; nothing is
written there). The generator is OCaml and is compiled against the
`compiler-libs` of the OCaml that made that build (`ocamlfind` in the path).
With `DECL_OUT=DIR` in the environment `run.sh` writes into `DIR` and not
into `decl/`, and with `DECLGEN_BUILD=DIR` it compiles the generator in
`DIR` and not under `_build/` (to compare what is made with what is
committed, and to make nothing in the folder: `tools/gate.sh` sets both).

## What a file says that it was made from

NO COMMIT IS GIVEN TO THE GENERATOR, AND NONE IS WRITTEN. What it writes
depends on what it reads and on nothing else: the same sources and a build
of them by the same OCaml give the same bytes, at whatever commit the tree
is and wherever the build is. So `decl/` can be made again from any
commit's own build and compared with what that commit has; and a change of
the compiler changes only the files of `decl/` whose inputs changed.

The comment GENERATED of each file names the file that it follows and then
the text of that file, as `(Git blob ID)`: the name that Git gives the
bytes of a file (the SHA-1 of the word `blob`, the length and the bytes;
`tools/declgen/blob.ml` computes it, Git is not called). For a commit C,

    git rev-parse C:PATH

prints the name of the text that PATH has at C, and `git log
--find-object=ID -- PATH` lists the commits that brought that text or took
it away. The 222 files name: the interface of the compiler's module (196
files); the file of Simplify whose own modules are declared (the 7 files
`FILE__local.v`); the tree's `stdlib/NAME.mli`, whose header the file
carries (19 files).

THE BUILD MUST BE A BUILD OF THOSE TEXTS, AND THE GENERATOR ASKS. A typed
tree (`.cmt`, `.cmti`) keeps the name of the text that the compiler read
and the MD5 digest of it. Before it writes a file the generator compares
that digest with the text of the tree (or with the copy that the build
made of it, which is one line that names the file and then the file), for:

- the typed tree of each of the 78 files of Simplify;
- the interface of every unit of the build whose compiled interface the
  compiler's library loaded for it (277 today: the 196 that have a file
  here, and 81 that only stand in the types of others);
- each implementation that it reads for `ARITIES.tsv`.

It also compares the digest of each compiled interface that was loaded
with the digest by which the 78 typed trees import that unit: a compiled
interface that was made again after a file of Simplify was compiled is
found so. IF ONE THING DIFFERS IT SAYS WHICH, WRITES NO FILE AND EXITS
WITH STATUS 2 (`the build compiled another text of PATH`). So the text
that a file names by its blob is the text from which the build compiled
what was read.

WHAT CANNOT BE COMPARED IS REFUSED IN THE SAME WAY. For a unit of the
build whose compiled interface was loaded, the generator wants the typed
tree that the compiler wrote with that compiled interface: the `.cmti`,
or the `.cmt` if there is no `.cmti`, beside the `.cmi`. Such a typed
tree keeps the digest of the compiled interface that was written with it,
and that digest must be the one that was loaded. The generator writes no
file and exits with status 2, with the reason, if that typed tree is not
there, cannot be read, was written with another compiled interface (as an
implementation's `.cmt` is, where the unit has an interface of its own),
names no text, or names a text that is neither in the tree nor in the
build root. It does so too if a compiled interface that was loaded is not
of the build and its unit is not of the standard library by its name
(`Stdlib`, `Stdlib__X`, `CamlinternalX`); and if a typed tree of an
implementation that the build has, and that is read for `ARITIES.tsv`,
cannot be read or compared.

A BUILD OF A PART OF THE COMPILER IS REFUSED IF THE PART IS TOO SMALL. The
number of parameters of a declared value is read from the typed tree of
the implementation of its unit (`ARITIES.tsv`). A build can have the
compiled interface of a unit, which is enough for the files of Rocq, and
not the typed tree of its implementation (`dune build
@middle_end/flambda2/simplify/check` alone makes such a build). The
generator then writes no file and exits with status 2, and names each
unit of the build for which that typed tree is not there (or is not that
of a whole implementation). It does not write a table in which the rows
of those units say `not read`. `tools/typedtrees.sh` makes a build that
has all that is read, without building the compiler.

ONE KIND OF TEXT THAT THE BUILD WROTE, AND THE TREE DOES NOT HAVE, IS
TAKEN: the list of the modules of a library, which dune writes (such as
`flambda2_terms.ml-gen`: a line `module A = Lib__A` for each module `A`
of the library `Lib`). 16 of the units that are loaded today are such
lists. A unit is taken as one only if all of this holds
(`list_of_modules` in `tools/declgen/src.ml`): the name of its text ends
with `.ml-gen`; that text is in the build root, has the digest that the
typed tree keeps, and begins with the line `(* generated by dune *)`; the
typed tree is that of an implementation and has an item; and every item
is `module A = Lib__A` for the unit's own `Lib`, or the empty module of
the unit's own name. Any other text that the build wrote is refused. The
generator prints the numbers when it ends, and one line `list of
modules:` for each list.

WHAT IS NOT COMPARED, AND IS NOT REFUSED.

- A UNIT THAT IS NOT OF THE BUILD, AND IS NOT OF THE STANDARD LIBRARY BY
  ITS NAME (`CamlinternalX`): if a value of it were declared, its row of
  `ARITIES.tsv` would say `not read`, with the reason, and nothing would
  be taken from its implementation. No such value is declared today.
- THE STANDARD LIBRARY. Its compiled interfaces are not of the build (the
  paragraph before "To make them again", and `PROVENANCE.md`, last
  section), so there is no text of the tree to compare (69 units are
  loaded; 19 have a file here). The comment GENERATED of each of the 19
  files says which compiled interface was read, by the MD5 digest that
  every compiled file which imports it keeps (`ocamlobjinfo` prints it
  beside the name of the unit). The generator has it from the compiled
  interfaces that were loaded and compares it, as above, with the one
  that the 78 typed trees keep. THAT DIGEST IS THE ONE BY WHICH OTHER
  UNITS IMPORT THE COMPILED INTERFACE OF THE UNIT, AND NO OTHER: it is
  neither the MD5 of the `.cmi` file nor that of the text of the
  interface. It changes when the compiled interface of the unit changes
  as a unit that imports it sees it; the file of that unit is then made
  again, and says so. A change of the library that leaves the compiled
  interface of a unit as it was (a change in an implementation alone)
  does not change the digest, and nothing here shows it. The blob beside
  it is that of the tree's `stdlib/NAME.mli`,
  of which the header alone is taken. The generator does not compare that
  header with the header of the library that was read (`PROVENANCE.md`
  says what was compared once, by hand).
- Named in no file: the OCaml that made the build, and the text of the
  generator itself. `tools/gate.sh` prints the versions of the programs.

## What is read, and how a thing is found

The typed trees (`.cmt`) of the 78 files say what each uses: every value,
every constructor built or matched, every field, every type written, every
exception, each resolved by the compiler's own environment. A file that
gives a module to a functor of its own (`Edge (Name.Map) (Name.Set)` in
`flow/data_flow_graph.ml`) uses, of that module, what the body of the functor
uses of its parameter (`Src_map.find` is `Name.Map.find`) and all that the
parameter's module type names; the modules of the
file are followed for that, through a structure written in the place and
through the result of another functor of the file. A module that a file
gives as a first-class module (`(module Coercion)` in `rebuilt_expr.ml`) is
used in the same way: all that the module type of that place names. After
`include X` in a
module of the file, where `X` is a module with a name, what the file names
without `X.` is a use of what `X` has. An abbreviation of
a module in a file of Simplify (`module DA = Downwards_acc`,
`Simplify_import.T`) is followed; a module that another interface makes an
alias (`Code_id.Map`, which is `Int_ids.Code_id.Map`) keeps the name that the
sources write, and its items are declared again under that name, its types
defined as the types of the module that it names. Then the interface (`.cmi`)
of each unit is walked in its own order, and what is used is declared, with
every type that a declared thing mentions (to a fixed point). `INDEX.tsv`:
OCaml name, Rocq name, kind, number of arguments, interface and line.

## The form (GUIDE.md has the rules; this is what the generator does)

- A function: `Parameter f : a -> b -> M c.` Arguments by place in the order
  of the interface; labels are dropped; every arrow, at any depth, has its
  result in `M` (so a callback is `a -> M b`), unless the result is an
  abbreviation of a function type (`... -> Simplify_common.rebuild a`): the
  `M` is then at the end of that one. Realised by its plain name.
- An optional argument: by place, of type `option a`; the realisation is a
  closed function that passes it with `?l:`.
- A function with a format (`Format.fprintf`): one declaration for each number
  of arguments after the format, `fprintf0` to `fprintf16`, and one for each
  greater number that a file of Simplify gives (`fprintf24`, `fprintf33`), the
  format a `string`, all realised by the same name.
- A value that is not a function: pure, `Parameter empty : t.`
- An exception: `Parameter E : exception payload.`, realised by a pair (the
  maker, the test). The real build can raise or handle it only if
  `payload` is `unit` or `string`; `make exceptions` refuses a declaration
  with a type that is spelt otherwise (GUIDE.md, section 4).
- A type that Simplify does not take apart: `Parameter t : Type.` With no
  parameter it has `Extract Inlined Constant t => "Mod.t"`: Rocq prints the
  string wherever the type is used. With parameters it has
  `Extract Constant t "'a1" => "('a1) Mod.t"` (Rocq has no inlined directive
  for a type with parameters): the string is for the type's definition, which
  is never printed since no file of decl/ is extracted; where the type is
  used, in a term or a comment, Rocq prints its name in Rocq, which is the
  compiler's when the modules have the compiler's names.
- An abbreviation: a `Definition`. So is a variant or a record that an
  interface gives again from another unit (`Coercion.t`, which is
  `Int_ids.Coercion.t`, also when its constructors are private): the two are
  one type in Rocq as in OCaml. A private abbreviation (`type t = private
  int`) stays abstract: it is not equal to its definition.
- A coercion of a private abbreviation (`(x :> int)`, where `x` is a NAME
  whose type is the private abbreviation `M.t`), where a file of Simplify
  writes one: a pure function, `Parameter coerce_t_to_int : t -> int.`,
  realised by the function that writes the coercion with both types
  (`(fun (x__1 : M.t) -> (x__1 :> int))`): a coercion runs nothing. It is
  declared directly after the type, in the module by whose name the file
  has the type, and once for each type that such a coercion gives; its name
  is the generator's, made of the last names of the two types. `INDEX.tsv`
  has it with the kind `coercion`. The typed tree keeps the type that a
  coercion gives and not the type of what is coerced, so only the coercion
  of a name is read; another one is said when the generator runs, and has
  no declaration.
- A variant that Simplify builds or matches: an `Inductive` with the
  compiler's constructors, and always an `Extract Inductive` that gives each
  constructor its qualified name in OCaml (so a constructor that had to take
  a `_` in Rocq is still printed right): Rocq prints `Mod.C (a, b)` in terms
  and in patterns. A constructor with an inline record takes the fields by
  place, in the order of the type; its string is a function of the tuple of
  its arguments, and the directive then has a third string, the match (one
  function for each constructor, then the scrutinee): a `match` of Rocq on
  such a type is printed as that function applied to one function for each
  branch. The same form, with the type written in the strings, for a variant
  one of whose constructors has the name of a constructor of a later type of
  its module (OCaml would take the bare name for the later type). No field of
  an inline record is a name of Rocq. `INDEX.tsv` gives the place of each
  field (`inline field`).
- A record whose fields Simplify reads or builds: a `Record` with the
  compiler's fields; a mutable field also has `set_FIELD`.
- A tuple with labels (`a * annotations:b * c`): a type of its own with one
  constructor, an `Inductive` with an `Extract Inductive`. Rocq has no label
  in a tuple, and OCaml refuses the tuple without its labels. The type's
  string is the tuple type of OCaml; the constructor's string is a function
  that makes the tuple with its labels from a plain tuple; the third string
  takes it apart, so a `match` of Rocq on it is printed as that function
  applied to the branch. One type for each such tuple type, declared in the
  module whose interface writes it first, before the item that writes it, and
  used wherever the interfaces write that tuple type. Its name is that of the
  labelled argument or of the field where it is first written, or else its
  own labels, then `_tuple`; its constructor has the same name with a
  capital: `Simplified_expr.arms_tuple` and `Arms_tuple`,
  `Upwards_env.handler_tuple`, `Downwards_env.forwarded_from_tuple`.
- Types defined together (`type a = ... and b = ...`): the abstract ones
  first, then the others, each after what it mentions; variants that mention
  each other are one `Inductive ... with ...`.
- A type that cannot be so (a GADT; a type that holds itself inside an
  abstract type; a record recursive with other types; a record with a field
  name already taken, or in a module inside a file whose name Rocq reserves):
  abstract, marked `PORT-GAP(type)`, with a pure maker `mk_C` for each
  constructor and one eliminator `match_T` whose branches are in `M`. (No
  maker for a private type: OCaml makes none outside its module. No
  eliminator for a GADT.)
- A module that a file of Simplify names by an alias exists, though empty.
- Every file ends with an empty module of its own name (`Module Simple. End
  Simple.` in `Simple.v`), which the interface does not have. It is there so
  that Rocq, of itself, writes no `open` of a file of decl/ in what it
  extracts. Without it Rocq's extraction
  writes `open U` in a file that uses a name of `U` that Rocq prints itself (a
  type with parameters, a record, a field, a module), and prints such names
  without `U.`. In OCaml that `open` brings every name of the real module,
  and Rocq knows only what is declared here (and of that, not what is an
  inlined string). So a short name could be a name of another opened module
  in OCaml (`Map.t` after `open Tag`: the compiler's `Tag` has a `Map`), and
  the head of a realisation could be hidden (`List` after `open Simple` is
  `Simple.List`). Rocq writes no `open U` when `U` has, at its top, a module
  with the name of a file in use, and `U` is in use where it would be opened.
  So with that last line Rocq prints each name of a file of decl/ in full
  (`Apply_cont_rewrite_id.Map.t`, `r.Flow_types.Acc.stack`). Only the `open`s
  that Rocq inserts by itself go. `open Port_monad` stays, and so does an
  `open` that a port file carries as OCaml text (such as `open
  Simplify_import`).

## Names

The compiler's, except: a word that Rocq reserves gets one `_` after it
(`Variable_`, `Set_`, `Import_`, `at_`); the unit `Stdlib` is `Stdlib_`. Rocq
has one name space where OCaml has several: a constructor or a field of a
mirrored type always keeps its name (Rocq prints it); a value or a type of the
same name in the module gets `_` (`descr_`), wherever it is declared, and so
does a second declaration of a name. Type variables are capitals (`'a` is
`A`). `INDEX.tsv` has every name.

## What the generator cannot translate, and what it does instead

| OCaml | what is done |
|---|---|
| labels | dropped: arguments by place |
| optional arguments | `option` by place, a closed function as realisation |
| format strings | a family by the number of arguments (0 to 16, and each greater number that a file of Simplify gives it: 24 and 33 now) |
| operators of `Stdlib` (`&&`, `<>`, `@`) | not declared: the kit and Rocq have their own |
| operators of other modules (`Code_size.(+)`, `let<*`) | a name spelled from the characters: `op_plus`, `let_op_lt_star` |
| functors | not declared. An instance that an interface names (`Variable.Map`) is a module like another |
| a functor of outside applied inside a file of Simplify | the module is declared in `FILE__local.v` (below). Not declared: `Set` and `Pair` inside the functor `Binary_arith_like` of `simplify_binary_primitive.ml`; the `include` of `non_constructed_code.ml` |
| module types | a module type of the compiler that a file of Simplify names from outside the file that defines it is a `Module Type` (below). Not declared: the others (6, in `NOT-DECLARED.tsv`), and a module type inside a module type |
| GADTs | abstract, with makers only (no eliminator: its branches could not have one type) |
| polymorphic variants | given as an index to an abstract type or a GADT (``[`Unarized] Flambda_arity.t``): dropped, with the parameter; each instance that the interfaces write is a named abbreviation of the type (`Flambda_arity.t_Unarized`, `t_Complex`), used where the interface has that instance and printed as the instance in OCaml; the bare `t` is where the interface has `'a t` or `_ t`. Elsewhere the declaration is left out |
| first-class modules, objects | the declaration is left out |
| a type with parameters in a module whose name Rocq reserves (`Variable.Map.t`) | it has its `Extract Constant` like another; where it is used Rocq prints `Variable_.Map.t`, so the runtime has `module Variable_ = Variable` |

## The modules that a file of Simplify makes for itself

A file of Simplify that applies a functor of another part of the compiler
(`module G = Strongly_connected_components.Make (Continuation)`), or has a
module with such an `include`, has a file `FILE__local.v` here: one `Module`
for each such module, in the usual form, with what the file uses of it. The
realisations name the module as the file does (`G.component`), so the port
keeps the module's definition in the extracted file as it is, and writes
`From SimplifyPort.decl Require Import FILE__local.` A module inside another
module of the file is inside a `Module` of that name
(`Rebuilt_expr__local.Matching_for_unique_handler.Match_permutable_parameters.HV`).
A `FILE__local.v` also ends with an empty module of its own name: it is no
module of OCaml, so an `open` of it could not be right. One thing in these
files is not an inlined string: the type `'a HV.t` of `rebuilt_expr.ml`, which
has a parameter. Where the port uses it Rocq prints its name in Rocq, the path
above with `.t`, which is no name of OCaml until the port of that file gives
it one.

| `flow/control_flow_graph.ml` | `G` |

## Module types, and the modules that a file gives to its own functors

A file of Simplify that has a functor of its own names module types of the
compiler for its parameters (`Container_types.S`,
`Number_adjuncts.Int_number_kind`, the module type
`Numeric_types.Float_by_bit_pattern`). Each module type of the compiler that
a file of Simplify names from outside the file that defines it (for a
parameter, or for a module inside the module type of a parameter) is a
`Module Type` of Rocq with ALL that the module type names, in the form of a
module: `Parameter`s, `Definition`s for the types that it defines, a `Module`
for each module inside. Its items have no directive and no row in
`INDEX.tsv`: Rocq honours no directive for what a functor uses of its
parameter and prints it by its name in Rocq (`N.Lhs.Set_.cardinal`). In Rocq
a module and a module type of one module cannot have the same name: the
module keeps the name and the module type takes one `_`
(`Numeric_types.Float_by_bit_pattern_`; and `Container_types.Set_`, since
`Set` is a word of Rocq). So where Rocq prints such a module type, or `Set_`
under a parameter, the name is not OCaml's: the port file has to give OCaml
that name.

A module that a file gives to one of its functors must have, in Rocq, all
that the parameter's module type names. So for each parameter of a functor
of a file, every value and every type that its module type names is declared
in each module that the file gives for it (also when the functor's body does
not use it). `FUNCTOR-ARGUMENTS.tsv` has one row for each module that is
given where a module type with a name is wanted: the file, the functor, the
module type and the module in OCaml, then both in Rocq. `compile_all.py`
gives each of these modules to a functor of Rocq whose parameter has that
module type, and so checks that Rocq takes it. A module type that is written
in the place with constraints (`Container_types.S with type t = Lhs.t *
Rhs.t`) has no row; what it names is declared all the same.

## `UPDATES.tsv`, `DONOR-TOKENS.tsv` and `DONOR-ITEMS.tsv`: the files of Simplify themselves

These three tables are not about what the port calls. They are about the
78 files that the ported files follow (the donors). `tools/given.py`
reads the first two (GUIDE.md section 4), `tools/lines.py` the last two
(GUIDE.md section 1). No file of decl/ depends on them. The same run
makes them (`tools/declgen/donors.ml`).

`UPDATES.tsv` has one row for each record update (a record written as
another record with some fields changed) of a donor, read from the typed
tree of its implementation, in seven columns:

1. the file;
2. the line where the update begins;
3. the line where it ends;
4. the type of the record, as the typed tree names it at that place;
5. the place of that type: the file and the line where its first field is
   declared, as the typed tree has them;
6. the fields that the update gives, in the order of the text;
7. all the fields of the type, in the order of the type.

Two types of one name in one file (a type `t` in each of two modules) have
two places, so the fifth column tells them apart where the fourth does
not. A row has names and numbers from the typed tree, and no text of a
source. A typed tree is read only if it was made from the text of the tree
(the rule at the end of the last section); if it was not, the donor has
one row with `-` for the two lines and for the place, and the reason in
the fourth column. Today: 157 rows, of 25 donors; no donor is "not read".

`DONOR-TOKENS.tsv` has one row for each donor, in three columns: the file;
the number of tokens that the compiler's own lexer reads in it (comments
left out); and a checksum, the MD5 of the characters of those tokens that
are not white space, one after the other, with nothing between one token
and the next (the white space inside a string is left out too).
`tools/given.py` reads the donors with a lexer of its own, and at each run
it wants this checksum for its own tokens: then it reads the same
characters that are not white space, outside comments, as the compiler's
lexer. The checksum is no identity of the tokens or of the source. It does
not show where a token ends: the two lexers do not cut the characters into
the same tokens (a label with its colon is one token of the compiler's
lexer, three of the tool's), so the numbers of tokens are not compared.
And it does not show the white space of a string; the tool's own
comparisons keep that (a string is one token with all its characters).
Today: 78 rows, 118437 tokens.

`DONOR-ITEMS.tsv` has one row for each name that an item of a structure
of a donor defines, at any depth of modules (also in the body of a
functor), read from the typed tree of its implementation, in eight
columns:

1. the file;
2. the kind: `value`, `external`, `type`, `exception`, `module`, `module
   type`;
3. the modules around the item inside the file, from the outermost, with
   dots between them, and `()` after the name of a functor; empty at the
   top of the file;
4. the name;
5. the first line of the definition of that name;
6. its last line;
7. the first line of the whole item;
8. the last line of the whole item.

The two pairs of lines differ for an item that defines several things
together: in `let rec f .. and g ..` the definition of `g` begins at its
own first line, and the item at `let`; so for the types of `type a = ..
and b = ..`. A value that a pattern binds (`let a, b = ..`) has one row
for each name, with the lines of the binding. An item that binds no name
(`let () = ..`) has no row; nor has what is not a definition (`open`,
`include`). A row has names and numbers from the typed tree, and no text
of a source. A donor whose typed tree was not made from the text of the
tree has one row, with `-` for the kind and the lines and the reason in
the fourth column. `tools/lines.py` compares the note of lines before
each definition of a ported file, and before each clause `with f` of a
`Fixpoint`, with these lines (its header says how, and which definitions
it does not judge). Today: 2024 rows (1472 values,
178 types, 358 modules, 11 module types, 5 exceptions), of 78 donors; 108
of them in the body of a functor; no donor is "not read".

For a test: `declgen --updates FILE.cmt` prints the rows of the record
updates of one typed tree, and `declgen --items FILE.cmt` the rows of its
items, whatever its source is; `declgen --tokens FILE.ml` prints the row
of one file.

## `ARITIES.tsv`: how many parameters each definition takes

The port gives a declared function its first arguments only (`papp1 f a`,
GUIDE.md section 2). In OCaml that runs nothing of `f` if the first group
of parameters that the definition of `f` WRITES ("The count", below) has
more parameters than `f` is given. An interface cannot say so (`val f : a
-> b -> c` may be `let f a = work (); fun b -> ...`); the definition can.
`ARITIES.tsv` has one row for each declared value (not for the values of a
module type), in five columns:

1. the OCaml name;
2. the Rocq name, as in `INDEX.tsv`;
3. the number of parameters of the function that the declaration writes as
   the realisation (`(fun x__1 x__2 x__3 x__4 -> Format.pp_print_list
   ?pp_sep:x__1 x__2 x__3 x__4)`, for a function with an optional argument);
   0 when the realisation is the name;
4. the number of parameters of the DEFINITION by the count below, read
   from the typed tree (`.cmt`) of the implementation; `-` when no
   definition was read;
5. the file and line of the definition (and, when the number is 0, what is
   written there in the place of a function literal), or why no definition
   was read.

Today, of 7137 rows: 3562 have a number above 0 (2 of them are external
primitives); 629 have 0 BY THE RULE OF WHAT IS WRITTEN: the definition is
not written as a function literal (a constant, a value that is built,
another name, an application, a `let` before the `fun`, as for
`Symbol.manufacture`), which does not say that the value is no function;
2946 are not read (the standard library).

`tools/lint.py` reads it (its last check, `tools/papp.py`): `pappN f` needs
no mark when N is smaller than column 3, or column 3 is 0 and N is smaller
than column 4. A row of the standard library has no number: the lint
leaves such a use to `make papp` ("What is not read", below). No file of
decl/ depends on it.

The table reads the COMPILER'S files. Where a file of Simplify is ported,
the program that is linked runs the definition of `extracted/` in its
place. `make papp` (`tools/papp.py --extracted`) is a second step after
the lint, and no check by itself: for each use that the lint passes by
column 4 with a place under `middle_end/flambda2/simplify/`, it looks for
the definition in the extracted file, in the module where the table has
the compiler's definition and nowhere else, as words, and wants more
parameters there too. A definition that it does not find there, or whose
parameters it cannot count, is an error. (`make papp` also judges each
`pappN` of a function of the file itself, by the file's own extracted
text; the table has no part in that: `tools/papp.py` and GUIDE.md section
2.)

The count. OCaml takes the parameters that ONE function literal writes
together as a GROUP, and runs nothing of the function until the group is
full. `let f p1 .. pn = B` is `let f = fun p1 .. pn -> B`: a group of n. A
parameter is a name, a pattern (`(a, b)`, `{ x; y }`, `()`, `lazy x`), a
labelled parameter, or an optional one, with or without a default (`?(x =
e)` is one parameter). The cases of a `function` directly after the
parameters are one more parameter of the same group: `let f a = function A
-> .. | B -> ..` has 2. If `B` is itself a function literal (`let f a =
fun b -> ..`), that is a SECOND GROUP: when the first group is full, OCaml
matches the patterns of its parameters and computes their defaults, and
only then gives the inner function. So `let f (lazy x) = fun y -> ..`
forces its argument as soon as it has one, `let f (Some x) = fun y -> ..`
can fail then, and `let f ?(x = e) = fun y -> ..` computes `e` then: each
counts 1. The count of a second group is added only if every parameter
before it is INERT: a variable or `_` (with or without a type or a label)
and no default. A pattern that only reads (`()`, a tuple, a record) is not
inert either. So `let f x = fun y -> ..` counts 2; and `let f (lazy x) y =
..` and `let f (lazy x) = function ..`, which are one group, count 2. (A
function whose interface shows an optional argument has a function as its
realisation: column 3 decides for it, not this number.) A type constraint
or a coercion around a function changes nothing. Anything else counts 0:
another name (`let f = g`), an application (`let f = g x`), a `let` before
the `fun`: OCaml runs it when the module starts, or the function that it
gives may act at its first argument. For `external f : .. = "p"`: the
number of arguments of the primitive. `_build/declgen/declgen --parameters
FILE.cmt` prints the count of each value that an implementation binds at
its top: for a test of this rule on made-up definitions.

How the definition is found: by the names, as OCaml finds it. From the
implementation of the unit, each module and then the value, with the LAST
binding of a name in a structure. `module A = B` is followed; an `include`
is followed into the module that it includes; the application of a functor
is followed into the body of the functor, where the parameter stands for
the argument (so `Continuation.Map.print` is at `patricia_tree.ml:2281`). A
thing that a file of Simplify makes for itself with a functor (the
`__local` files) is found in that file by its identifier.

What is not read; the row says why.
- The standard library: 2946 rows (`Format`, `List`, ..; and what a functor
  of the compiler takes from `Map.Make`, `Set.Make` or `Hashtbl.Make`). The
  standard library of the tree is compiled by the tree's own compiler, and
  the OCaml that builds `tools/declgen` does not read those typed trees:
  the table has no number for these rows. For a function of it that a use
  gives its first arguments (`pappN`), `make papp` reads the tree's own
  `stdlib/` AS WORDS, and only for a value of a unit of the library itself
  (`List.map` in `stdlib/list.ml`; not what a functor makes, which is most
  of these rows). The use needs no mark when the definition there has
  more parameters than the use gives arguments, or when its realisation
  is a function (column 3); else it keeps the mark `PORT-GAP(papp)`.
  No DEFINITION is read of the standard library of the compiler that
  BUILDS the tree, with which a compiler of the first stage is linked:
  that library is not of this repository (`tools/papp.py`, THE STANDARD
  LIBRARY, says what the reading of words does not establish). Its
  compiled interfaces are read, as before: they are the interfaces of the
  standard library that the build read, and the types of what decl/
  declares of `List`, `Option`, .. are theirs; such a declaration names
  the tree's own file of the same name (`stdlib/list.mli`).
- A module that is made from a value (a first-class module), and whatever
  else could not be followed: no row today.

What is read, and is it the text of the tree? For this table
`tools/declgen` reads the typed trees and, besides them, the BYTES OF THE
SOURCE FILES (of the tree, and of the build's copies), only to compare them
with a digest. It writes none of their text: a row has names and numbers
from the typed tree, and the place. A typed tree names its
source and has the digest of the text that the compiler read. A unit is
read only if that is the digest of the same file under SOURCE_ROOT, or the
build's file is a copy that the build made of a file of the tree (the line
`# 1 "utils/misc.ml"`, then exactly that file). The list of the modules of
a library that dune writes (`flambda2_types__.ml-gen`: lines `module A =
Flambda2_types__A`, perhaps an empty module, and no more) is no file of the
tree: it is read, and it defines no value.
